# Scenario: Baseline Authorization Load Test

## Purpose

First runnable SVT scenario for `authz-agent`. Exercises all currently implemented
authorization endpoint families under a deterministic, CSV-driven workload with
paired canonical and legacy measurements.

## Endpoint Coverage

| Canonical | Legacy Equivalent | CSV Source |
| ----------- | ------------------- | ------------ |
| `POST /access/v1/authorize` (1 resource) | `POST /access/v1/check/resource` | `requests.csv` |
| `POST /access/v1/authorize` (filter-style) | `POST /access/v1/check/filter` | `requests-filter.csv` |
| `POST /access/v1/authorize` (N resources) | `POST /access/v1/check/resource/bulk` | `requests-bulk.csv` |

## Dataset

| Parameter | Value |
| ----------- | ------- |
| Resource types | `ORDER`, `CUSTOMER`, `PRODUCT`, `INVOICE`, `DOCUMENT` |
| Operations per type | `CREATE`, `READ`, `UPDATE`, `DELETE`, `LIST`, `EXPORT`, `IMPORT`, `APPROVE`, `REJECT`, `ARCHIVE` |
| Users | `svt-admin`, `svt-manager`, `svt-operator`, `svt-viewer`, `svt-restricted` |
| Unauthorized share | ~10% of CSV rows result in DENY |
| PIP policies | none (first stage excludes GENERAL PIP) |
| Complex RLS user | `svt-restricted` (conditions: `resource.ownerId == subject.email`, `resource.regionId == subject.email`) |

## User/Role Matrix

| User | Role | Access Level |
| ------ | ------ | ------------- |
| `svt-admin` | `ROLE_SVT_ADMIN` | All 5 resource types, all 10 operations |
| `svt-manager` | `ROLE_SVT_MANAGER` | All 5 resource types, 8 operations (no REJECT/ARCHIVE) |
| `svt-operator` | `ROLE_SVT_OPERATOR` | ORDER/CUSTOMER/PRODUCT only, 5 operations (CRUD + LIST) |
| `svt-viewer` | `ROLE_SVT_VIEWER` | All 5 resource types, READ only |
| `svt-restricted` | `ROLE_SVT_RESTRICTED` | ORDER/CUSTOMER only, READ/UPDATE/LIST with RLS conditions |

## Execution Model

The test plan runs in one of two modes, controlled by the `mode` property:

- `mode=canonical`: only canonical thread groups are active (legacy thread count = 0)
- `mode=legacy`: only legacy thread groups are active (canonical thread count = 0)

The `run` wrapper script executes both modes sequentially, producing separate result
artifacts for each.

Each active mode uses three thread groups with `ConstantThroughputTimer` rate shaping.
The stage-level `target_rps` value is split evenly across those groups, and acceptance for the
default tuned profile is `1000 RPS ±25 RPS` over the configured stage duration.
The default wrapper profile runs two sequential `1`-minute stages: canonical first, then legacy.

## Token Strategy

Tokens are acquired once by the `run` script before the measured run and passed to
JMeter via a properties file. Each thread group resolves the token for the current
CSV row's `username` using `props.get("token_<username>")`. No token acquisition
happens inside the JMeter hot path.

## Configurable Properties

| Property | Default | Description |
| ---------- | --------- | ------------- |
| `mode` | `canonical` | `canonical` or `legacy` |
| `threads` | `30` | Concurrent threads per active thread group |
| `ramp_seconds` | `5` | Thread ramp-up period |
| `duration_seconds` | `60` | Total test duration per stage |
| `target_rps` | `1000` | Aggregate stage-level throughput target (split across 3 groups, accepted at ±25 RPS) |
| `authz_host` | `authz-agent` | Target hostname |
| `authz_port` | `8080` | Target port |

## Input Files

- `/data/requests.csv` — single-resource request mix (50 rows, ~10% unauthorized)
- `/data/requests-filter.csv` — filter request mix (20 rows, ~10% unauthorized)
- `/data/requests-bulk.csv` — deterministic bulk request mix with explicit request class and expected decision
- `/tokens.properties` — pre-acquired Keycloak tokens (generated by `run` script)

`requests.csv` stores raw JSON fragments in the `resourceJson` column. When a row contains
embedded double quotes inside that JSON, the cell must be RFC4180-quoted so JMeter preserves a
valid JSON fragment when `${resourceJson}` is interpolated into request bodies.

The `expectedFilterResult` column in `requests-filter.csv` mirrors what the
`/access/v1/check/filter` endpoint actually returns once the
`subject.emailFromToken` TOKEN PIP is seeded (it is — see
[tests/svt/common/compose/seed/svt-pips.json](../../common/compose/seed/svt-pips.json)
and `tests/svt/scripts/up`): `ALLOW` for unconditional rules and
`USE_FILTER_CONDITION` for rsqlPredicate-bearing rules (JMeter classifies
both as `ALLOW`). The two genuine-deny rows and the conditional
`svt-restricted ORDER READ` row keep `DENY`. Before the PIP was seeded,
RLS-conditioned rows short-circuited to DENY and the column carried
`DENY` everywhere — that state is no longer correct.

## Output

- JTL result file per mode (canonical/legacy)
- JMeter HTML dashboard per mode

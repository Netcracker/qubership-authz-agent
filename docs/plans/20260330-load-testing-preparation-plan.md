## Goal

Prepare a repeatable, compatibility-safe load-testing baseline for the currently implemented
Authz Agent surface so the split local stack (`envoy` public entrypoint with backend `opa` and
`decision-log-collector`) can be exercised toward a stage-local `1000 RPS` target with an accepted
`±25 RPS` tolerance band, without changing authorization semantics or the OPA decision boundary.

### Requirements

1. Target load for the first benchmark wave is `1000 RPS` through Envoy against the local Authz
   Agent stack.
2. The first milestone is environment preparation for load testing, not product tuning.
3. Load testing is executed locally with the application stack and supporting tooling started via
   Docker Compose.
4. Resource measurements must be collected through `cAdvisor`, scraped by `Prometheus`, and
   visualized in `Grafana`.
5. Request load must be generated by `JMeter`.
6. Every load-testing scenario must be measured twice: once through the canonical endpoint and once
   through the corresponding legacy endpoint flow, with semantically identical request composition.
7. Throughput acceptance is evaluated separately for the canonical stage and the legacy stage:
   each stage must land within `1000 RPS ±25 RPS` aggregate across all samplers in that stage,
   measured over the configured stage duration.
8. The primary benchmark path remains Envoy-boundary, but an additive internal-only OPA-direct
   diagnostic profile is allowed when it reuses the same semantic dataset and the same
   single/filter/bulk ratio as the main baseline (ADR-0034).

## Scope

- Cover only the currently implemented public authorization routes:
  - `POST /access/v1/authorize`
  - `POST /access/v1/check/resource`
  - `POST /access/v1/check/resource/bulk`
  - `POST /access/v1/check/filter`
- Optionally include `GET /health` as an operational smoke signal for benchmark setup.
- Reuse the current runtime boundary (`envoy` + backend `opa` + `decision-log-collector` +
  Keycloak) and existing policy/PIP upload flow inside a dedicated local Docker Compose-based load
  environment.
- Store all load-testing repository assets under `tests/svt/`.
- Fix `JMeter` as the load generator for benchmark traffic.
- Fix `cAdvisor` + `Prometheus` + `Grafana` as the resource-observability stack for local runs.
- Require paired canonical-vs-legacy measurements with semantically identical request sets.
- Allow an additive internal-only OPA-direct diagnostic profile that reuses the same semantic
  request mix and the same per-family throughput ratio as the main baseline, while remaining
  separate from compatibility/public-route benchmark results.
- Define deterministic workload fixtures, token strategy, startup/reset flow, and environment assets
  for repeated local runs.
- Define measurement outputs for JMeter request metrics plus container resource usage/artifacts from
  the observability stack.
- Prepare repository structure, scripts, dashboards, and documentation for environment shakeout,
  smoke profiles, and later benchmark profiles.
- Keep deferred legacy/v2 endpoints out of scope; their current `404` behavior remains unchanged.
- Do not tune product code or change the OPA/Envoy architecture inside this planning phase.

## Risks

- Local Docker Compose runs are environment-specific; absolute `1000 RPS` results will be misleading
  unless host specs and container limits are recorded consistently.
- A tight stage-local `1000 RPS ±25 RPS` acceptance band still requires explicit rate shaping or
  deterministic tuning; a pure concurrency-driven JMeter profile can overshoot or undershoot even
  when the system has available headroom.
- `JMeter` and the system under test share the same local host resources unless the Compose setup
  isolates them carefully, which can distort both latency and throughput.
- `cAdvisor` provides container-level resource metrics, not request-level latency breakdowns, so
  JMeter must remain the source of truth for request throughput and latency percentiles.
- Token acquisition through Keycloak can dominate measurements if it happens inside the hot request
  path instead of setup/warm-up.
- GENERAL PIP calls can turn a pure authorization benchmark into a remote-dependency benchmark
  unless those scenarios are separated deliberately.
- OPA decision logging, debug logging, or policy-admin traffic can skew measurements if they are
  enabled during benchmark runs without being accounted for.
- Large bulk requests can shift the bottleneck from authorization logic to JSON serialization and
  memory pressure; those scenarios need separate baselines.
- Deferred legacy/v2 endpoints must stay out of the workload matrix until a separate implementation
  handover brings them back into scope.
